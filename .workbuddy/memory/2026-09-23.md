# 打包成单文件 exe（内带 ngspice）+ 顺带挖出并修掉一个并发竞态

用户要求：「打包成exe文件，方便使用。」

四个技术分叉先问过用户，全部按推荐项定：

| 分叉 | 选择 | 理由 |
|---|---|---|
| 打包形态 | **onefile** | 拷一个文件就能跑 |
| `ngspice.dll`（7.1 MB） | **打进包** | 目标机不装 KiCad 也三法齐全 |
| `runs/` 与 `config/` | **exe 同级** | 便携，整个文件夹能搬走 |
| 控制台窗口 | **保留** | 出问题能看见原因 |

## 修掉的问题（按发现顺序）

### 1. onefile 的数据根陷阱
解压目录 `_MEIPASS` **退出即失**。原来的 `ROOT = Path(__file__).parents[2]`
冻结后就指向临时目录 → `runs/`（用户上传的原件、会话）退出全没，**且不报错**。
修法：资源根（只读）与数据根（可写、exe 同级）分开，数据根每一级都带
`data_root_reason`，首屏与 `/api/health` 都显示。

### 2. `probe_availability()` 的谎言
旧实现只做 `import PySpice` + 设 `LIBRARY_PATH` 就宣布可用。
**打包后每一个 ngspice 调用都失败**，而横幅写着「● ngspice 可用」、
报告页也显示可用，**没有任何地方告诉用户**。
改用判据：真跑一次 1V/1Ω 的 `.op`，`V(1)=1.0` 与 `|i|=1.0` 都对才算可用，
并把 `verified` 打在首屏（"已实跑一次最小 .op 并核对结果"）。

### 3. ★ PySpice 的 `api.h` 没被打进包
正是第 2 条让这个坑暴露出来：加了真跑探测之后，exe 里探针立刻报
`FileNotFoundError: .../_MEI.../PySpice/Spice/NgSpice/api.h`。
根因：PySpice **运行时读数据文件**，PyInstaller 默认只收 `.py` 与二进制。
修法：`collect_data_files("PySpice", include_py_files=False)`（实测恰好
`api.h` + `logging.yml` 两个）。**源码环境一切正常**，所以只在打包后出现。

### 4. ★★ 并发竞态：`CDefError: duplicate declaration of struct ngcomplex`
修完第 3 条后，exe 里探针仍报这个错，而**真解却过了** —— 自相矛盾。
在源码环境单独调探针是**通过**的，所以不是打包问题。

读 PySpice 源码定位到两处进程级全局状态：

1. `Shared.py:110` 的 `ffi = FFI()` 是**模块级单例**，`_load_library()` 每次
   构造实例都无脑 `ffi.cdef(api.h 全文)` —— **第二次 cdef 必抛 duplicate**。
2. `NgSpiceShared._instances` 按 id 缓存，但"查缓存→构造→写回"**不原子**。

所以**两个线程同时第一次构造，必崩一个**。实测（8 线程同时首调探针）：
**1 成功 / 7 失败**，失败者全是同一条 CDefError。
谁会并发进来：FastAPI 的同步端点跑在**线程池**里，启动那一刻启动器的就绪轮询
与外部检查会**同时**打 `/api/health`。
最终缓存成不成功看调度 → 表现为"同一道题偶尔报求解失败、重试又好了"，
**单线程怎么跑都复现不出来**。这条也威胁 `ngspice_method`（两个并发 `/api/solve`）。

修法：`app/solver/ngspice.py` 的 `_NG_LOCK`（`RLock`），**探针与真解共用同一把锁**
（抢的是同一份全局状态，分两把等于没加）；`probe_availability()` 双检锁；
`ngspice_method` 变薄壳，实体是 `_solve_locked`（只在持锁时调用）。
修后同一诊断：**8/8**。

### 5. 横幅自相矛盾
`● 视觉大模型  已配置  （模型 X，**缺 key**）` —— 绿点 + "已配置" 却缺 key。
`will_call_vlm` 只算「通道开着 + 升级策略不是 never」，**没看 key**。
改成缺 key 时显示 `○ 缺 key —— 需要升级时调不起来`。
`tools/verify_exe.py` 新增第 ⑦ 节盯住这条。

### 6. 重建失败的哑报错
`PyInstaller 返回 1`，1 秒就退出，看不出原因（撞过一次）。
新增 `_exe_locked()`。**判据是实测选的**：运行中的 exe
**改得了名**（`rename` 成功 → 第一版判据永远漏判）、
删不掉、`open("r+b")` → `Permission denied`（**这才是有效判据**，且非破坏性）。

### 7. ★★ onefile 的孤儿进程（收尾没收干净）
验证脚本收尾只 `terminate()`，跑完发现 `tasklist` 里**还剩两个 `circuit_agent.exe`**。
查 `Win32_Process` 的父子关系才明白：PyInstaller 的 onefile 是
**父进程解压 → 再 `CreateProcess` 一个子进程跑真应用**，父进程只是等着。
于是 `subprocess.Popen` 拿到的是**父**进程 —— 杀掉它，那个正在跑服务、
占着端口与 `%TEMP%\_MEI*` 的**子进程成了孤儿**。

修法：`stop_tree()` 用 `taskkill /PID <父pid> /T /F`，
**必须在父进程还活着时执行**（父一死就找不到子）；收尾再断言
**端口真的释放了** —— 比"进程对象说它退了"可信。

### 8. ★ `ignore_errors=True` 把清理失败藏住了
`shutil.rmtree(work, ignore_errors=True)` —— 因为孤儿子进程还占着里面的文件，
删除**一直失败**，而我从没见过任何提示。结果 `%TEMP%` 里悄悄攒了 **8 个
`ca_verify_*`**。改成不忽略错误 + 断言目录真的没了。

### 9. ★ 残留解压目录：3.0 GB
顺着第 8 条查下去，`_MEI*` 残留 **19 个 / 3,030 MB**（每次解压 252.5 MB，
比 exe 本身还大一倍）。正常退出由引导器删，**强杀就漏**。

`launcher.sweep_stale_mei()`：**三道闸门** —— ① 只认临时目录顶层的 `_MEI*`；
② 时效门槛 2 小时（太新的不动：刚启动的实例正在往自己那个目录解压，
此时可能还没有打开的文件句柄，光靠第 3 条判不出来）；
③ **改名试锁** —— 实测运行中的 `_MEI` 目录 `rename` 会「拒绝访问」，
改名成功就等于没人用它；删不掉就改回原名，不留 `.stale` 怪名。
自己的 `sys._MEIPASS` 永远跳过。清理结果**打在首屏**（几个、多少 MB），
绝不悄悄删。实测回收 **3.44 GB**，`busy: 0`。
新增 `tests/test_temp_sweep.py`（沙箱里跑，含"持句柄时不许删"的对照）。

## 结果

- `dist/circuit_agent.exe`：**105.9 MB**，冷启动 4.5 秒
- `tools/verify_exe.py` 在**空目录**里端到端：**失败项 0**
  - 路径分家（`data_root` = exe 同级、`_MEIPASS` 里**没有** `runs/`）
  - 三法齐全、来源是**包内自带**、`verified` 非空
  - OCR 可用（`zh-Hans-CN`）、`opencv 5.0.0 / scipy 1.18.1`
  - 纯 R/V：三法互校过、`i = 1/400`（手算 2.5 mA）、ngspice 那一路有值
  - 含 C/L：`overall_pass`、节点 = `10/3 V`
  - `runs/` 与 `config/` 真的建在 exe 同级
  - 日志按 cp936 正确解码；缺 key 时横幅不说「已配置」
  - 收尾：端口已释放（无孤儿子进程）、临时目录**真的**删掉了
- **九套全 0 失败** + **跨工具对账差异项 0** + 画布静态自检 **0 失败**
- 首屏横幅现在把「判定依据」写出来了
- 顺手回收 `%TEMP%` 里 **3.44 GB** 历史残留
