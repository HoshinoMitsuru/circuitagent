用户要求：「打包成exe文件，方便使用。」

四个技术分叉先问过用户，全部按推荐项定：

| 分叉 | 选择 | 理由 |

## 修掉的问题（按发现顺序）

### 1. onefile 的数据根陷阱
解压目录 `_MEIPASS` **退出即失**。原来的 `ROOT = Path(__file__).parents[2]`
冻结后就指向临时目录 → `runs/`（用户上传的原件、会话）退出全没，**且不报错**。
修法：资源根（只读）与数据根（可写、exe 同级）分开，数据根每一级都带
`data_root_reason`，首屏与 `/api/health` 都显示。

### 2. `probe_availability()` 的谎言
旧实现只做 `import PySpice` + 设 `LIBRARY_PATH` 就宣布可用。
**打包后每一个 ngspice 调用都失败**，而横幅写着「● ngspice 可用」、
报告页也显示可用，**没有任何地方告诉用户**。
改用判据：真跑一次 1V/1Ω 的 `.op`，`V(1)=1.0` 与 `|i|=1.0` 都对才算可用，
并把 `verified` 打在首屏（"已实跑一次最小 .op 并核对结果"）。

### 3. ★ PySpice 的 `api.h` 没被打进包
正是第 2 条让这个坑暴露出来：加了真跑探测之后，exe 里探针立刻报
`FileNotFoundError: .../_MEI.../PySpice/Spice/NgSpice/api.h`。
根因：PySpice **运行时读数据文件**，PyInstaller 默认只收 `.py` 与二进制。
修法：`collect_data_files("PySpice", include_py_files=False)`（实测恰好
`api.h` + `logging.yml` 两个）。**源码环境一切正常**，所以只在打包后出现。

### 4. ★★ 并发竞态：`CDefError: duplicate declaration of struct ngcomplex`
修完第 3 条后，exe 里探针仍报这个错，而**真解却过了** —— 自相矛盾。
在源码环境单独调探针是**通过**的，所以不是打包问题。

读 PySpice 源码定位到两处进程级全局状态：

1. `Shared.py:110` 的 `ffi = FFI()` 是**模块级单例**，`_load_library()` 每次
   构造实例都无脑 `ffi.cdef(api.h 全文)` —— **第二次 cdef 必抛 duplicate**。
2. `NgSpiceShared._instances` 按 id 缓存，但"查缓存→构造→写回"**不原子**。

所以**两个线程同时第一次构造，必崩一个**。实测（8 线程同时首调探针）：
**1 成功 / 7 失败**，失败者全是同一条 CDefError。
谁会并发进来：FastAPI 的同步端点跑在**线程池**里，启动那一刻启动器的就绪轮询
与外部检查会**同时**打 `/api/health`。
最终缓存成不成功看调度 → 表现为"同一道题偶尔报求解失败、重试又好了"，
**单线程怎么跑都复现不出来**。这条也威胁 `ngspice_method`（两个并发 `/api/solve`）。

修法：`app/solver/ngspice.py` 的 `_NG_LOCK`（`RLock`），**探针与真解共用同一把锁**
（抢的是同一份全局状态，分两把等于没加）；`probe_availability()` 双检锁；
`ngspice_method` 变薄壳，实体是 `_solve_locked`（只在持锁时调用）。
修后同一诊断：**8/8**。

### 5. 横幅自相矛盾
`● 视觉大模型  已配置  （模型 X，**缺 key**）` —— 绿点 + "已配置" 却缺 key。
`will_call_vlm` 只算「通道开着 + 升级策略不是 never」，**没看 key**。
改成缺 key 时显示 `○ 缺 key —— 需要升级时调不起来`。
`tools/verify_exe.py` 新增第 ⑦ 节盯住这条。

### 6. 重建失败的哑报错
`PyInstaller 返回 1`，1 秒就退出，看不出原因（撞过一次）。
新增 `_exe_locked()`。**判据是实测选的**：运行中的 exe
**改得了名**（`rename` 成功 → 第一版判据永远漏判）、
删不掉、`open("r+b")` → `Permission denied`（**这才是有效判据**，且非破坏性）。

### 7. ★★ onefile 的孤儿进程（收尾没收干净）
验证脚本收尾只 `terminate()`，跑完发现 `tasklist` 里**还剩两个 `circuit_agent.exe`**。
查 `Win32_Process` 的父子关系才明白：PyInstaller 的 onefile 是
**父进程解压 → 再 `CreateProcess` 一个子进程跑真应用**，父进程只是等着。
于是 `subprocess.Popen` 拿到的是**父**进程 —— 杀掉它，那个正在跑服务、
占着端口与 `%TEMP%\_MEI*` 的**子进程成了孤儿**。

修法：`stop_tree()` 用 `taskkill /PID <父pid> /T /F`，
**必须在父进程还活着时执行**（父一死就找不到子）；收尾再断言
**端口真的释放了** —— 比"进程对象说它退了"可信。

### 8. ★ `ignore_errors=True` 把清理失败藏住了
`shutil.rmtree(work, ignore_errors=True)` —— 因为孤儿子进程还占着里面的文件，
删除**一直失败**，而我从没见过任何提示。结果 `%TEMP%` 里悄悄攒了 **8 个
`ca_verify_*`**。改成不忽略错误 + 断言目录真的没了。

### 9. ★ 残留解压目录：3.0 GB
顺着第 8 条查下去，`_MEI*` 残留 **19 个 / 3,030 MB**（每次解压 252.5 MB，
比 exe 本身还大一倍）。正常退出由引导器删，**强杀就漏**。

`launcher.sweep_stale_mei()`：**三道闸门** —— ① 只认临时目录顶层的 `_MEI*`；
② 时效门槛 2 小时（太新的不动：刚启动的实例正在往自己那个目录解压，
此时可能还没有打开的文件句柄，光靠第 3 条判不出来）；
③ **改名试锁** —— 实测运行中的 `_MEI` 目录 `rename` 会「拒绝访问」，
改名成功就等于没人用它；删不掉就改回原名，不留 `.stale` 怪名。
自己的 `sys._MEIPASS` 永远跳过。清理结果**打在首屏**（几个、多少 MB），
绝不悄悄删。实测回收 **3.44 GB**，`busy: 0`。
新增 `tests/test_temp_sweep.py`（沙箱里跑，含"持句柄时不许删"的对照）。

# 附录：打包参考全录（MEMORY.md 因体积上限移出，细节以此为准）

四个决策（用户确认）：**onefile** / **ngspice.dll 打进包** / **runs+config 放 exe 同级** /
**保留控制台**。工具链 `tools/build_exe.py`（4 步）+ `tools/verify_exe.py`（干净目录端到端）。

- **资源根 ≠ 数据根**（`app/paths.py`）：onefile 的资源根是 `_MEIPASS`（退出即失），
  数据根是 **exe 同级**。不分家则 `runs/` 落进临时目录、**退出就没了且不报错**。
  `resource_root()`（只读，web/ 与 vendor/ 在此）vs `data_root()`（可写，便携 →
  `%LOCALAPPDATA%` → 临时目录，**每一级都带 `data_root_reason`**）。
  测试/探针仍 monkeypatch `server.RUNS_DIR`，所以 `RUNS_DIR` 保持模块级全局。
- **`bundled_ngspice()` 排在 KiCad 之前**（环境变量仍最优先）：先用自己的那份，版本才是
  测过的那个。`origin` 字段如实说明来源。
- **探针必须真跑一次 `.op`**，不能只 `import`。旧实现只 import → 横幅写「● ngspice 可用」
  而第三法其实是空的，**且没有任何地方告诉用户**。现在判据是「跑完 1V/1Ω 并核对
  V(1)=1.0 与 |i|=1.0」，并把 `verified` 字段打上首屏。
- **★ PySpice 的 `api.h` / `logging.yml` 是运行时读的**数据文件，PyInstaller 默认只收
  `.py` 与二进制 → 必须 `collect_data_files("PySpice", include_py_files=False)`
  （实测恰好这两个）。**不打包时一切正常**，打出来之后每道题的第三法都失败。
  症状：`CDefError`／空结果，且真实求解"看起来"还对。
- 另需 `collect_submodules("winrt")`（命名空间包 + 原生扩展，OCR 的 import 在函数体里，
  静态分析看不到；少收的表现是"OCR 不可用"这个**看起来完全正常**的降级分支）
  与 `collect_submodules("uvicorn")`（协议/事件循环是运行时按名挑的）。
- `vendor/ngspice/`（dll + `LICENSE.ngspice.txt`）**必须入库**：它是构建输入，不是产物。
  没它则构建出的包**悄悄只剩两法**。发版时 `dist/THIRD-PARTY-NOTICES.txt` 要和 exe 一起给。
- 重建失败若只有一句 `PyInstaller 返回 1`：用 `_exe_locked()` 判 —— 判据是
  `open(path, "r+b")` **Permission denied**（实测：运行中的 exe **改得了名**、删不掉、
  打不开写；用 rename 判会永远漏判）。

## 附录 A：onefile 是"父进程 + 子进程"，只杀父进程会留孤儿

PyInstaller 的 onefile 形态：**父**进程把包解压到 `_MEI*` → 再 `CreateProcess`
一个**子**进程跑真应用，父进程只是等着。所以 `subprocess.Popen` 拿到的是**父**进程：

- 只 `terminate()` 父进程 → 正在跑服务、占着端口与 `%TEMP%\_MEI*` 的**子进程变孤儿**。
  症状：下次启动报"端口被占"、临时目录删不掉、`runs/` 行为异常。
  必须 `taskkill /PID <父pid> /T /F`，且**要在父进程还活着时执行**（父一死就找不到子）。
- `tools/verify_exe.py` 的 `stop_tree()` 就是干这个的；收尾还断言
  **端口真的释放了**（比"进程对象说它退了"可信）。

## 附录 B：残留解压目录：强杀一次漏 ~250 MB（`sweep_stale_mei`）

单文件模式每次启动往 `%TEMP%\_MEI*` 解压 ~250 MB（比 exe 本身大一倍），
正常退出由引导器删掉；**只要上次是被强杀的**就留在那里。实测本机被测一下午
攒了 **19 个 / 3.0 GB**。`launcher.sweep_stale_mei()` 在启动时清，**三道闸门**：

1. 只认临时目录**顶层**的 `_MEI*`，别的文件/目录一律不碰；
2. **时效门槛**（默认 2 小时）：太新的不动 —— 刚启动的实例正在往自己那个目录里
   解压，那时可能还没有任何打开的文件句柄，光靠第 3 条判不出来；
3. **改名试锁**：Windows 上**在被使用的目录改不了名**（实测「拒绝访问」，
   因为引导器持有目录句柄且未开 `FILE_SHARE_DELETE`）。改名成功 = 没人用它，才敢删；
   删不掉就改回原名，不留 `.stale` 怪名。自己的 `sys._MEIPASS` 永远跳过。

`CIRCUIT_AGENT_NO_TEMP_SWEEP=1` 可关；`CIRCUIT_AGENT_TEMP_SWEEP_AGE` 覆盖门槛（测试用）。
**绝不悄悄删**：清理了几个、回收多少 MB 都打在首屏横幅上。
测试 `tests/test_temp_sweep.py`（沙箱里跑，四道闸门逐个盯，含"持句柄时不许删"的对照）。

★ 同理教训：`tools/verify_exe.py` 原来写 `shutil.rmtree(work, ignore_errors=True)`，
把"删不掉"完全藏住了 —— 于是悄悄攒了 8 个临时目录。**清理失败必须能被看见。**

## 附录 C：控制台输出的编码

冻结 exe 的输出在重定向时用**系统 ANSI 代码页**（cp936），不是 UTF-8。
`verify_exe.py` 的 `read_log()` 用 `BANNER_MARK = "电路读图"` 作为判定依据来选编码 ——
**不能**只靠解码异常来猜（不同多字节编码存在重叠），也不能假设 UTF-8。
横幅的显示宽度用 `unicodedata.east_asian_width` 算（`len("位图通道")` 给 4，
而等宽终端渲染 8 列）。
