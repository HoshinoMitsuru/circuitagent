## 修复：连通层把「符号本体」当导线 → 元件自我短路（核心缺陷）

发现的根因链（三个独立缺陷叠在一起，全都不报错）：

1. **`into_seg` 判据符号写反**（`app/ingest/topology.py`）
   槽位轴线 p→q，p 端导线应朝 −u、q 端应朝 **+u**。旧代码要求两端都 < −0.7，
   于是**真槽位必然被拒、假槽位必然被接受**（两根线同向在同一侧）。
   持续表现：6 个元件只挑出 1~2 个，且挑出的都是"跨元件"的假配对。
   → 改判据为 `op·u < -0.7 and oq·u > +0.7`。

2. **`max_gap=220` 卡掉长元件** → 槽位挑不出来 → 本体没剔除 → 短路。
   改为 `DEFAULT_MAX_GAP = 500`，并把"空隙里有图形"升级为
   **"同一件连通图形必须横跨两个端子"**（`_one_glyph_spans`），
   空隙长度被图形自身尺度自然框住，不需要靠 max_gap 硬卡。

3. **图形只看 rect/circle/arc，看不到电容极板** → 电容槽位永远挑不出。
   → 新增 `_glyph_items`，把「垂直于轴线的短线段」也算图形。

### 短路本身的机理（必须记住）
电阻框是四条边首尾相接的**闭环导体**；两根导线分别画到框的左右边中点，
于是 左导线 → 框左边缘 → 框角 → 框右边缘 → 右导线，**元件用自己的符号把两端短接**。
两个电学结点被并成一个，**不报错**，解出来的数还看着合理。
解法：先挑槽位 → 算「元件本体圆柱」(`slot_region`) → 把**完整落在圆柱内**的线段从导线图剔除 → 再建连通图。
`build_topology` 的顺序因此固定为 **槽位 → 本体剔除 → 连通 → 元件**。

## 新发现（待拍板）：`from_spice` 读不回自己写的网表

**实跑证据**（`runs/_chk_spice.py`）：

```
from_spice(to_spice(circ))  →  CircuitError: V1 的数值 'DC' 不是字面数字
```

原因：`to_spice()`（`app/ir/spice.py:29-30`）**故意**给电压源写 `DC` 前缀
（注释：避免 ngspice 在 .op 下自作主张），但 `from_spice()`（:83-90）只做裸
`float(vtxt)` —— **自家写出的网表自家读不回**。任何含电压源的电路往返必断。

第二个缺口：`app/ingest/values.py::parse_engineering` **已经完整支持** `1k / 4k7 / 1meg / 10u`，
但 `from_spice` 根本没调用它，仍在用裸 `float()`。所以：

| 写法 | 现状 |
|---|---|
| `V1 1 0 12` | 读通 |
| `V1 1 0 DC 12` | **报错**（自家 to_spice 的输出） |
| `V1 1 0 DC=12` | 报错 |
| `R1 1 2 1k` / `4k7` / `1meg` / `C1 1 2 10u` | **报错**（解析器其实已具备能力，只是没接上） |
| `V1 1 0 AC 1` / `SIN(...)` / `PULSE(...)` | 报错 |

**报错信息本身也是错的**：它写"不解析…（如 {R1} 或 1k 之外的杂式）"，
暗示 1k 能解析 —— 实际不能。这条提示语必须改，否则误导。

AC/SIN/PULSE 被拒**本身是对的**（本工具只解直流工作点；`V1 1 0 AC 1` 甚至根本没有直流值），
但错误信息该精准说明"这是交流/瞬态激励"，而不是"不是字面数字"。
→ 扩大解析范围属于**技术分岔**，已摆选项待苏霖韵拍板，未擅自实现。

## 位图通道的技术储备（下一步直接借鉴）

`parse_schematic_img.py` 里有几处比现成方案更省事、值得照搬：

1. **`ink_mask`**：`ndimage.uniform_filter(gray, size=61)` 求邻域均值，
   像素比均值暗 `delta=22` 以上判为墨迹 —— **局部自适应二值化**，抗纸面阴影/渐变。
   文件注释里写明"本图右下明显偏暗"，全局阈值会把阴影吃成墨迹。
2. **`_runs`**：用**定向开运算**（横/竖结构元 `binary_opening`）筛长线段，再 `label` 连通标记。
   比 Canny + Hough 简单得多，而且天然只留横竖两类（电路图就是这两类）。
3. **`merge_collinear`**：把被文字/箭头打断的同一根线合回来（同轴 ±6px、区间相接）。
4. **`find_dots`**：实心结点圆点 = 唯一能熬过半径 r=5 圆盘腐蚀的东西（线宽远小于 2r）。
5. **★ 最有价值的一条：用「度数」筛假圆点，而不是调半径。**
   文字笔画（尤其中文粗体）、箭头三角也能熬过腐蚀，
   但它们**悬在空白处、度数只有 0~1**，而真结点圆点度数 ≥3。
   "用度数筛掉，比调半径可靠得多" —— 这条思路比参数调优高一档。
6. **接点分类与本项目判据一致**（独立得到同一结论）：
   有圆点→相连；无圆点+十字（度≥4）→**不相连**；无圆点+T（度3）→相连。
7. **落在器件框内的接点要跳过** —— 因为框长边端点碰到框的另一条边，不是电路意义的十字。
   **这与本项目那条"符号本体不是导线"是同一个坑，被独立踩到并独立解决。**
8. **悬空端点分 5 类**（比本项目现在的二值 `dangling_endpoints` 细）：
   真悬空 / 元件端子 / 转角(歪斜) / 文字笔画 / 电流箭头。
   后四类**都不是缺陷**，一刀切会把正常图报成满屏问题。
9. **回答了我上一轮提的分岔**：照片透视歪斜 6~20px 时，那份工具**没有做透视校正**，
   而是把 `--tol` 放大到覆盖歪斜，配合手工 `--crop` / `--rot` / `--scale`。
   且它据此成功产出了 4-17 与电桥两份网表（注释写明"据几何解析结果抄写，不是据肉眼"）。
   → 自动透视校正的收益/风险比不划算，倾向照它的路子走。
10. 一处 Python 细节值得记：它的 `near(a, b, tol=None)` 注释提醒
    **不要写 `def near(a,b,tol=TOL)`** —— 默认参数在定义时求值，
    之后改全局 `TOL` 对它无效，会出现"命令行给了 `--tol 20` 但仍按 4px 判"的隐性 bug。

用户需求原文：「补充视觉逻辑：优先OCR模板化识别，无法本地识别即调用后台存储的
apiurl和apikey使用大模型识别。默认使用deepseek的视觉模型。」

用户拍板的四个分岔：
1. 本地 OCR 引擎 → **Windows 内置 OCR**
2. VLM 职责边界 → **优先对视觉大模型最大信任**（本地失败时整体采信 VLM 的网表，
   而不是只让它补几个字）。注意「最大信任」≠「隐去不确定性」：
   仍记 `source="vlm"`、留原始返回、跑叠图核对。
3. 落地顺序 → **一次做完整两级**
4. 密钥存储 → **`config/secrets.local.json` + WebUI 设置入口**
5. 另追加一条（本轮新问）：**本地成功门槛 = 分级**。只有**结构性**失败
   （符号定位不到、导线追踪不出、拓扑有歧义）才调 VLM；
   **非结构性**失败（某电阻数值读不清、位号认成 RI）本地照样出网表，
   把那一格标 `needs_human` 交人填，不花这笔钱。
   依据：「不许靠肉眼定连接」针对的是**连接**，数值读不清是另一类问题。
   → 落成 `VisionConfig.escalate_on = "structural" | "any" | "never"`。

## ★★ Windows OCR 的能力边界（全部真机实测，不是推断）

这一段的每一条都值得记住，因为**其中三条推翻了上一轮记录的说法**。

### A. 短文本行会被**静默丢弃**（最要命的一条）
单独渲染的 `R1`/`C1`/`V1`/`I1`/`L1`/`L2`/`1k`/`1M`，在 24/32/40/48/60
五种字号下**全部返回空**。不是认错，是版面分析阶段整条就没被当成文本。

**救不回来**（全部实测否定）：加导线、加矩形框、`stroke_width=1/2` 描边、
字号放大到 100px、整图缩放 0.5/1.0/1.5/2.0、白底黑字换黑底白字、
横向+纵向形态学膨胀（纵向膨胀 ky>9 后**全图返回空**，比不处理更糟）。
唯一有效的是「这一行本身有足够多的字」：`R1 10k` 同行能读出 `RI 1 Ok`。
但真实版式里位号在上、数值在下，本就是两行 —— 所以这条帮不上忙。

**后果**：真实原理图里 `R1`/`C1` 这类两字符位号**大概率读不到**。

**对策（已实现）**：`ocr.py` 除了跑 OCR，还**独立做一遍几何文本块检测**
（连通块尺寸/长宽比/填充率，不依赖 OCR），把 OCR 结果覆盖不到的文本块
报成 `dropped`（「有字但没读出来」）。实测有效：一张含 R1/10k/C1/100uF
的合成图，OCR 只读出两个数值，`dropped` 准确指出了 R1 与 C1 的坐标。
→ 这就把「静默降级」变成了显式报告。

### B. 能读出来时的混淆规律（修正表的事实依据）
- `1` → `I`：`R11`→`RI 1`、`R1 10k`→`RI 1 Ok`
- `0` → `O`：`0.1uF`→`O.1uF`、`10k`→`Ok`
- 小数点 → `．`(FF0E) / `·`(B7) / `，`(FF0C) / `。`，**甚至直接消失成空格**：
  `4.7k`→`4 7k`、`3.3V`→`3 3V`、`0.01uF`→`0 01uF`
- `m` 被拆成 `rn`：`2.2mH`→`2 2rnH`
- `V` 被当成汉字：`3.3V`→`3 ． 3 伊`
- **纯数字加单位很可靠**：`10k`/`100uF`/`12V`/`220`/`2N3904` 全字号正确

### C. 环境与 API（三个坑，都踩过）
- `Language` 在 `winrt.windows.globalization`，**不在** `media.ocr`
- `OcrEngine` **没有** `max_image_dimension` 属性
- `try_create_from_language` 对未安装语言返回 `None`，**不抛异常** ——
  所以「引擎建不出来」和「语言没装」表现为同一件事，必须靠回退链处理。
  这台机器只装了 `zh-Hans-CN`；`en-US`/`ja-JP`/`zh-Hant-TW` 都没有。
- `SoftwareBitmap.create_copy_from_buffer` 只收 **4 个参数**
  （buffer, format, w, h）。多传 alpha mode → `TypeError: Invalid parameter count`
  （报错完全不提参数个数，极易往「格式不对」方向查错）。
- `bounding_rect` 的 `Rect` **不可迭代**，必须取 `.x/.y/.width/.height`
- `recognize_async` 返回 `IAsyncOperation`，`.get()` 同步取结果，但**是阻塞的**
  → 在 FastAPI 的 async 端点里调用必须放进线程池
- `inspect.signature` 对 winrt 内建函数无效，别指望它探签名

### D. 修正表的铁律（防误伤比修正更重要）
修正**只作用于位号与数值这两个语法位置**，绝不作用于自由文本
（`RI` 在图纸说明里可能真的就是 `RI`）。

- 位号：**首字母绝不动**。`I1` 是合法电流源位号，改成 `11` 会把元件类型改掉，
  而且三法会一致地给出同一个错答案。所以「开头字母当数字」只认 `O`/`o`
  （依据：标准位号类别字母**不含 O**）。
- 「两个字母的 token 第二个其实是数字」只认 `I/l/|/!`→`1`、`O/o`→`0` 这一张窄表。
  反例：`LED` 的末位 `D` 在宽表里对应 `0`，放宽就会改成 `LE0`；
  `RT`（热敏电阻）会被改成 `R7`。
- 数值：字母→数字只在**紧邻数字**时动手，这样 `12V` 的 V、`100uF` 的 u/F、
  `4k7` 的 k 都不会被动。
- `auto` 判定法：两条路都走一遍，修完之后「以数字打头」→ 判数值，
  「符合位号形状」→ 判位号，两边都成立时看原始首字符。
  **必须这样**，因为 OCR 的错误会让 token 形状失去判别力 ——
  `Ok` 是 `0k` 被读坏的样子，可它看起来完全像一个字母打头的位号。
- 每一条修正都写进 `OcrWord.fixes` 并保留 `raw` 原文，可逐条核对。

实测结果：20 条应修正全过 + 25 条防误伤全过。

# 先审后算：OCR 校对表 + 手动升级（WebUI 功能层）

用户需求原文：「图片OCR识别后，先提交在UI界面，允许用户手动补充编辑和修正，
由用户手动选择是否进提交LLM识别照片；允许用户直接手动在UI上索引到绘制面板，
直接手动绘制电路图。保持操作方式简洁清晰，且对元件具有高度兼容性。
如果已有好用的工具或者应用，直接移植，避免重复造轮子。」

## 落成的四段流程

导入（`tier=local`，**不花钱**）→ 校对表改文字 → `POST /api/vision/ocr` 重算（毫秒级）
→ `POST /api/vision/escalate` 由用户按按钮花钱。

### ★ 重放语义（本轮的核心设计）

编辑清单**永远从「机器原始读数」重放**，不在上一次结果上累加。于是：
改错了真的回得去、不需要撤销栈、重复点结果永远一致。
端到端实测：`10k` → 改 `22k` → `22000.0` → 清空清单 → **回到 `10000.0`**。

落地方式：`LocalOutcome` 拆出 `ocr`（原始，**永不覆盖**）与 `ocr_effective`（生效）；
会话里只存 `vision_ocr_edits` 清单，不存结果。
★ 自己写出来的 bug：第一版写了 `loc.ocr = res`，把「已校对的那份」当成新基线 ——
于是清空清单后数值**没有还原**。这就是重放语义必须有的那道防线。

### ★ Windows OCR 对位号的杀伤面（`runs/_probe_refdes_scan.py`，比上一轮记录更严重）

20px 逐字符渲染后送 OCR：

| 前缀 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| R | ∅ | ∅ | R3 | ∅ | R5 | ∅ | R7 | R8 | R9 |
| C | ∅ | ∅ | C3 | ∅ | C5 | ∅ | C7 | C8 | C9 |
| V | ∅ | ∅ | V3 | ∅ | ∅ | ∅ | ∅ | ∅ | V9 |
| L | ∅ | ∅ | ∅ | ∅ | ∅ | ∅ | L7 | ∅ | ∅ |
| I | ∅ | ∅ | ∅ | `》` | ∅ | `》` | ∅ | ∅ | `》` |

`R1` 在 16/20/26/32/40px **每一档都被整条吞掉**（5/5 丢），而 `R3`/`R5` 认得到 ——
**没有任何规律**。教科书里最常见的 `R1`／`C1`／`V1` 恰好全在丢失集里。
`I` 组更差：1~9 里 6 个丢、3 个吐乱码 `》`。

→ 推论（重要）：**「位号读不出来」在真实照片上是常态，不是边缘情况**。
   管线在位号缺失时走 `Circuit.auto_ref` 自动编号 —— 所以「结构确认」表里的
   `R1`/`R2` **多半是我们编的号，不是图上写的**。
   WebUI 的校对卡因此补了一段专门说明，把「补位号」和「网表里的名字」绑起来讲。

## 修掉的问题

1. **`tests/test_api.py` 有 7 行是语法错**：字符串里混进了 ASCII 直引号
   （`banner("…停在"等你过目"这一步")`）→ `SyntaxError`，**整个测试文件跑不起来**。
   换成「」。
   ★ 定位手段值得记：一开始用「CJK 旁边的引号」扫，把正常的分隔引号全捞进来了；
   正确判据是「**左右紧邻都是汉字**的引号才是内层引号」（`("` 左边是 `(`、
   `")` 右边是 `)`，都不满足）。

2. **测试自己的读数 bug**：`dropped_after = eff.get("dropped") or raw.get("dropped")` ——
   补填**成功**时 `dropped` 正好是空列表 `[]`，`[] or B` 会穿透到原始那份（仍有 1 条），
   于是「修好了」被读成「没修好」。

## 2. 修掉一个真缺口：连续改第二次时「原件」被手绘版顶掉

`/api/from-svg` 改第一次之后 `sess.source_path` 已指向 `hand.svg`。

## 3. 补上 Ctrl+Z / 重做（原来撤销栈是死的）

探针捞出来的：`dUndo` 只有按钮接线，**没有快捷键，也没有重做**。
